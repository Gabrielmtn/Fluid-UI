# Frame time and layout (F2) — notes

A 60 s CDP performance trace of the shipping web build in headless Chrome, three times: the sim running idle, then a top-bar fader dragged with trusted mouse moves, then idle again. From each trace: frame intervals (median, p95), long tasks, Layout / UpdateLayoutTree / Paint / PrePaint / Layerize / Commit per frame, forced synchronous layouts, and what `window.__stats` and `window.__perf.probe()` expose. This is the "no regression beyond run-to-run noise" and "no new forced layouts per frame" gate for the Walnut & Copper prep. Written by `prep/baseline/scripts/perf-trace.js`. Captured 2026-10-17 13:45–13:49Z at HEAD `c4796da` with Chrome 155.0.8059.80 (headless), viewport 1440×900 CSS px, DPR 1, `--ui-scale` 1, canvas 864×741, GPU `ANGLE (NVIDIA, NVIDIA GeForce RTX 4090 (0x00002684) Direct3D11 vs_5_0 ps_5_0, D3D11)`, Node v25.9.0.

**Headless numbers are relative, not the user's machine.** Headless Chrome paces `requestAnimationFrame` from its own synthetic BeginFrame source (measured here: a rAF tick every 7.63 ms, ~131 Hz; the app's probe snapped it to "120 Hz"), the app's FPS Limit of 60 then draws on every other tick (~65 drawn frames a second, 15.3 ms apart), and nothing waits for a display. The GPU is the real RTX 4090 through ANGLE/D3D11 (not SwiftShader), but the pacing, the 60 cap and the headless compositor make every absolute number a property of this rig and this Chrome. The gate is the same capture before and after a CSS step on the same machine, read against the noise measured here; it says nothing about Gabriel's 144 Hz panel or the Electron build.

## How to run

```bash
node prep/baseline/scripts/perf-trace.js             # capture: 3 runs -> prep/baseline/perf/  (about 4.5 min)
node prep/baseline/scripts/perf-trace.js --check     # one more run -> prep/work/perf-check/, compared with the baseline; exit 1 on any flag (about 1.5 min)
node prep/baseline/scripts/perf-trace.js --summarize # rebuild summary.md from the run-<n>.json already there (no Chrome)
node prep/baseline/scripts/perf-trace.js --check --compare prep/work/perf-check/run-check.json            # re-read an earlier check, no capture
node prep/baseline/scripts/perf-trace.js --check --baseline <dir>                                          # compare against another capture's run-<n>.json
node prep/baseline/scripts/perf-trace.js --runs 1 --phase-seconds 3 --out prep/work/perf-smoke            # a smoke run that does not touch the baseline
```

**Run it alone.** One headless Chrome at a time, nothing else rendering: a second Chrome, a running Electron build or a video playing shares the GPU and the compositor and inflates the numbers silently (`scripts/test/PERF.md`, rule 2). No dev server, no Electron, no `npm install`, nothing on port 9333: the script boots its own Chrome through `scripts/test/radial-menu/driver.js` (own static server on the repo root, scratch profile with PhotoSafe, the startup fork, the first-run hint and the Reset-app note already answered, trusted input over CDP) and closes it in a `finally`. `CHROME=` overrides the browser. The script re-executes itself with `--max-old-space-size=8192` when Node's default heap is under 6 GB: a 60 s trace is a 162 MB JSON text and parses into well over a gigabyte of objects.

## What a run does, in order

1. `boot({ seed: { 'swirlResetHint.v1': '1' } })`, `Emulation.setDeviceMetricsOverride` 1440×900 @1, a reload (the driver's `load()`: navigate, wait for the app, hide `#photoWarn`, wait for the splash, 600 ms), so `--ui-scale` and the canvas are computed for that viewport.
2. Environment: `Browser.getVersion`; `scripts/test/perf-harness.js` injected for `window.__perf.probe()` only (its `measure()` and `pin()` are never called: `pin()` disables the governor through `QualityGovernor.setEnabled`, which persists); the page facts listed under *Files*. The GPU string is `WEBGL_debug_renderer_info` → `UNMASKED_RENDERER_WEBGL`, with `gl.RENDERER` (`WebKit WebGL`) and the vendor beside it.
3. Wait for the quality governor's boot ascent (js/08a-quality-governor.js `BOOT_STAGES`: the sim starts at half resolution and steps up once measured fps proves out, a framebuffer reinit): `dyeScale()` and `simScale()` back at 1, no `needsFramebufferReinit`, `__stats.fps > 0`, `document.getAnimations().length === 0`, all stable for 3 s; give up after 30 s and record the parked state. Settled after 3.15–3.16 s in every run, one state change (the ascent had already finished by the first poll).
4. One trusted stroke across the canvas (`Input.dispatchMouseEvent`: press, 48 moves 16 ms apart on a sine path, release), so there is dye to move. `probe-dye.js` measured it with the harness: dye coverage 19 % after the stroke.
5. `Tracing.start` with exactly the brief's categories (`devtools.timeline,disabled-by-default-devtools.timeline,disabled-by-default-devtools.timeline.frame,blink.user_timing,v8.execute`), `recordUntilFull`, `ReturnAsStream`; a page-side timer that samples `__stats`, the governor level, `dyeScale()` and `#curl` every 500 ms for the whole trace (the same `TimerFire` in every phase and every run).
6. Three phases of 20 s, each opened and closed with `performance.mark('pt:<phase>:start|end')` so the trace itself carries the boundaries on its own clock (`blink.user_timing`), plus `__drawSerial`, the governor state and the fader value at each boundary:
   - **idle1**: nothing but the sim and the UI's own timers.
   - **drag**: press on the `#curl` fader (the canonical `<input type="range">` inside `.mixer-channel[data-ui-key="Fluid"] .ch-fader`; `#curl` has no perceptual proxy, js/20-mixer-layout.js:943–1052 lists `brushSize`, `densityDissipation`, `timeScale`, `colorBlend`), then ~60 trusted `mouseMoved` events a second sweeping the track on a 4 s sine, release just before the phase ends. 1194–1195 moves in 19.9 s = 60.0 Hz, max gap between moves 38–40 ms. The value swept 0–58 in every run.
   - **idle2**: idle again.
7. `Tracing.end`, `IO.read` the stream, gzip it to `trace-<n>.json.gz`, parse, analyse (below). Run time 83.4 s per run.

Nothing here calls an app setter that persists (GUIDANCE.md §2b): the only state changes are trusted pointer events on real controls inside the scratch profile, which the driver deletes on close. The governor is left exactly as shipped and its level is recorded at every phase boundary (L0, scales 1/1, throughout every run and both checks).

## How the metrics are computed

- **Renderer process**: the `TracingStartedInBrowser` frame whose URL ends in `index.html`; its `CrRendererMain` and `Compositor` threads from the `thread_name` metadata.
- **Main-thread events**: `X` events plus paired `B`/`E` on `CrRendererMain`, sorted by time, nested by containment. Each event knows its depth, its parent and the chain of script events above it (`FunctionCall`, `EventDispatch`, `TimerFire`, `FireAnimationFrame`, `EvaluateScript`, `RunMicrotasks`, `V8.Execute`, …).
- **Phase windows**: the `pt:*` marks (`analysis.phaseSource: "marks"` in every run; a wall-clock fallback exists and would be reported as a problem).
- **Frame** (the "/ frame" denominator): `BeginMainThreadFrame` count on the main thread, the main-thread frame in which style recalc, layout, paint and commit run. Not `FireAnimationFrame`: one rAF tick fires every registered callback back to back (6–7 here: 05j `update`, the jank monitor, light source, light shift, the audio cue editor and audio scenes, the brush cursor), so that event counts callbacks, 6.4 per tick. rAF ticks are recovered by grouping `FireAnimationFrame` events with gaps over 2 ms and equal the main-frame count exactly (2609 = 2609, …).
- **Frame interval**: `DrawFrame` to `DrawFrame` on the Compositor thread, the frames actually drawn; equal to the app's own `__drawSerial` delta while idle (1305 = 1305) and above it while dragging (1526–1604 compositor frames for 1300–1306 app frames: the fader thumb and readout repaint between the app's capped draws). Median, p95, mean, max. rAF tick intervals and `BeginMainThreadFrame` intervals are reported beside it.
- **Frame work per tick**: the sum of one tick's `FireAnimationFrame` durations (the app's main-thread frame work); single-callback p95 is informational.
- **Long tasks**: `RunTask` events (present in these categories) longer than 50 ms; the five longest top-level tasks of each phase are listed with their biggest children.
- **Per frame / ms per frame**: `Layout`, `UpdateLayoutTree`, `Paint`, `PrePaint`, `Layerize`, `Commit`, `CompositeLayers`, `UpdateLayerTree`, `HitTest`, `EventDispatch`, `FunctionCall`, `TimerFire` counts and summed durations divided by frames; `mainBusy` = all depth-0 main-thread time per frame.
- **Forced synchronous layouts**: `Layout` events nested inside a script event (JavaScript asked for geometry before the frame's own layout); forced style recalcs the same for `UpdateLayoutTree`. The parent histogram separates them from the frame's own layout (parent `RunTask`), and `layoutSites` names the innermost script site (`FunctionCall <function> <file>:<line>` or `EventDispatch <type>`). `Layout` events carry no `stackTrace` without `disabled-by-default-devtools.timeline.stack`, so DevTools' own "forced reflow" flag (`layoutsWithStack`, always 0 here) is not available; nesting is the signal.
- **`__stats`**: fps, frametime, lastCpuMs, budgetPct from the 500 ms samples inside each phase (39–40 per phase), plus the governor levels and dye scales seen and the `#curl` range.

- **Idle is layout-free.** With the sim running, 20 s of idle produce zero Layout, zero UpdateLayoutTree and zero Paint on the main thread; every main frame is PrePaint → Layerize → Commit only (the canvas), 0.27 ms of main-thread time per frame. The 500 ms sampler and the perceptual fader poll (250 ms, js/20 `startPerceptualFaderPoll`) are the only timers (0.161 TimerFire per frame) and neither dirties layout.
- **Dragging a fader forces one synchronous layout per value change.** 563 / 561 / 563 forced layouts and the same number of forced style recalcs in 20 s, 0.216 per main frame, matching the 566–568 `InvalidateLayout` / `ScheduleStyleRecalculation` events: every `input` event on `#curl` writes the fader's `--val` custom property and the readout text (js/05h-slider-bindings.js:402–404 for curl: `cSlider.style.setProperty('--val', …)`, `cSpan.textContent = …`), and the next rAF callback that reads geometry forces the dirty style and layout. The two sites are the app's frame function `update` (js/05j-update-loop.js:389; it reads `canvasWrapper.clientWidth` / `clientHeight` at 05j:547–548 every frame) and the audio cue editor's `draw` (js/40b-audio-cue-editor.js:122; `cv.offsetParent` at :124, a layout-forcing read, before `cv.clientWidth` at :131). Which of the two pays depends on callback order in that tick, so the **split moves run to run (281/282, 335/226, 266/297) while the total is stable (noise 2)**; only the totals and per-frame rates are gated. None of this is CSS; it is in the open items.
- **Nothing is slow.** No long task anywhere (the longest top-level task in 180 s of trace was 9.45 ms, a `Commit`); main-thread frame work p95 is 0.42 ms while dragging; `__stats.lastCpuMs` p95 0.2–0.4 ms; `budgetPct` 0.6 %. The main thread is idle 97 % of the time in every phase; the frame interval is set by the headless pacing and the app's 60 cap, not by work.
- **The frame interval median drops while dragging** (15.3 → 14.7 ms) because the compositor draws extra frames for the fader thumb and the readout between the app's capped draws (DrawFrame 1573 vs `__drawSerial` 1304 over 20 s); the app itself still drew 65 frames a second. This is why the drag phase has 8× the interval noise of the idle phases (0.24 vs 0.03 ms).
- `CompositeLayers` does not exist in Chrome 155's timeline (its work is `Layerize` + `Commit`); the row is kept at 0 so a later Chrome that emits it is noticed.
- Governor L0, scales 1/1, `#slowdownCell` absent, no page exceptions, no problems, in every run and both checks.

## What `--check` does

`--check` captures one more run the same way (into `prep/work/perf-check/run-check.json` + `trace-check.json.gz`), then compares every **gated** metric per phase with the baseline: mean and noise = max − min over the three baseline runs, gate = mean + noise (higher is worse for every gated metric). The gated set (17 per phase, 51 in all): frame interval median and p95, frame work per tick p95, long tasks, Layout / UpdateLayoutTree / Paint / PrePaint / Layerize / Commit / CompositeLayers per frame, Layout / UpdateLayoutTree / Paint / main-busy ms per frame, forced synchronous layouts per frame, forced style recalcs per frame.

Two rules, both reported: **count rows** (per-frame counts, forced layouts, long tasks) are flagged on anything above the gate, the brief's rule as written: a metric that is 0 in all three baseline runs has gate 0, so **any** forced layout or any Layout / Paint in an idle phase fails, which is "no new forced layouts per frame". **Timing rows** (`interval.*`, `frameWork.*`, `msPerFrame.*`) also have to exceed the gate by a **2 % floor** (`--tolerance-pct N`; `0` is the literal rule). The floor exists because the literal rule failed an unchanged app: the second check was above the gate on three timing rows by +0.2 %, +0.3 % and +0.8 % (28 µs on a 15.3 ms median, 1 µs on frame-work p95, 70 ns per frame of style recalc). Three runs bound 51 metrics too tightly for microsecond scheduling noise (the chance that a fourth sample of a noisy metric lands above the first three's envelope is of order one in four); 2 % lets those through and still flags a per-frame style recalc that grows from 0.024 to 0.074 ms (+200 %) or frame work that grows by a fifth. The verdict and the exit code follow the floored rule; the literal count is printed beside it (`literal rule: n worse`) and every row above the gate but inside the floor is listed as such in `check.md`, so nothing is hidden.

It writes `prep/work/perf-check/check.md` (every row with baseline, mean, noise, gate, value and `ok` / `above the gate by …, within the floor` / `WORSE (+x, +y % of the gate)`), prints the flagged rows, and exits 1 on any flag. The environment facts (Chrome, viewport, GPU, resolutions, drag target) are listed when they differ but do not fail the gate; a baseline captured with a different `--phase-seconds` or move rate is refused. `--compare FILE` re-evaluates an earlier check's JSON without a capture; `--baseline DIR` compares against another capture.

Reading a flag: a flag on forced layouts, Layout / UpdateLayoutTree / Paint per frame, long tasks, or a new entry in `phases.drag.forced.layoutSites` / `styleRecalcSites` of the check's run JSON is the real signal for a CSS step. A timing flag just over 2 % deserves one re-run before it is believed; one of 20 % or more does not.

| What could move | Cause | Pin |

## Caveats

- **Headless, not Electron, not a display** (see the top). The Electron build differs by the titlebar, the window fade and a real vsync; the Steam machine spread is a different question (`scripts/test/PERF.md` has the uncapped tier ladder for that).
- **The frame interval is a pacing number.** The app runs rAF at ~131 ticks/s here and draws every other tick under its FPS Limit of 60; the median is 15.3 ms whatever the UI does, until main-thread work exceeds a tick. The sensitive rows for a CSS step are the per-frame counts and milliseconds, the forced layouts and the frame work per tick, not the interval.
- **One drag target, one width.** The Fluid fader at 1440 wide; the `#curl` value also drives `config.CURL` (hijacked as a material macro while Material type is `fluid`, `scripts/test/inventory/params.json`), so the sim's vorticity varies 0–58 during the drag; that is GPU work and does not reach the main-thread metrics. Dragging a sidebar slider, the colour well, a select, or a keyboard-driven change is not covered; the script's `FADER_PREFERENCE` falls back to the next strip fader (and records a problem) if the Fluid cell were parked in the More panel.
- **No `.stack` category**, so forced layouts are identified by nesting (a Layout under a FunctionCall / EventDispatch / TimerFire), not by DevTools' stack-trace flag.
- **The gate's floor is a choice.** The brief says mean + noise; that rule, applied to 51 metrics with three-run bounds, failed an unchanged app on microseconds (second check), so the timing rows carry a 2 % floor and the count rows do not. The value 2 % and the split between the two kinds of row are on the open items for Gabriel; `--tolerance-pct 0` gives the literal rule, and both verdicts are always printed.
- **Noise with three runs is a lower bound on noise.** Four runs (three baseline + two checks) spread idle1 `frameWork.p95` over 0.234–0.253 ms (8 %) and `msPerFrame.UpdateLayoutTree` over 0.0233–0.0243 (4 %), both wider than the three-run envelope. More baseline runs would widen the gates honestly; `--runs N` does that at 85 s a run.
- The 500 ms `__stats` sampler and `window.__perf` (perf-harness.js, probe only) are in the page during the trace; both are identical in every run and in `--check`.
- Chrome 155 names: `PrePaint` + `Layerize` + `Commit` are the modern lifecycle; `CompositeLayers` is not emitted. `UpdateLayerTree` 0.
