## 0. Test-day blocker: what is live is NOT what is in the repo

Probed `fluid-ui-multiplayer.gabrielmtn.partykit.dev` directly:

| capability | live relay | repo |
|---|---|---|
| cap-8 private rooms (`capacity: 8`) | yes | yes |
| server-authored forgery filter | yes | yes |
| heartbeat / zombie reaper | yes | yes |
| `turnMode: "stroke"` ("One swirl each") | **no** | yes |

The live **web bundle** (`?v=mt59p9ei`) is behind too — no "One swirl each" option, no
share-mode/QR room panel, none of the unified-button work.

**The trap:** if the new client ships without the new relay, picking *One swirl each* gives a
rotation with no clock **and no auto-pass**. The client falls back to `turnModeLocal = 'timer'`
(06:1600), so `isOneSwirlMode()` (06:1075) is false and the client-side stroke-end pass never
fires; the relay has no deadline to enforce either. The brush sits with one person until
somebody presses *Pass turn*.

**Do:** `npm run deploy` (build:web + partykit deploy) before the test. Client and relay must
ship together. Then re-probe to confirm `mode: "stroke"` comes back.

## 1. Severe at 8 people

### 1.1 Inbound paint load is unbudgeted and scales linearly with peers — the headline risk

Measured, 8 clients painting flat-out through the relay:

```
one splat message         3584 B (relay cap 16384)
per client, received      300 msgs/s   726 KB/s
relay totals              813 KB/s in  5806 KB/s out   fan-out 7.00x
peer dabs arriving        ~19,200 /sec at each client
```

Your own brush is frame-budgeted: `BRUSH_DAB_BUDGET` 4000 dabs per simulated second, drained
once per frame (05j:247). **Received dabs are not.** `handleRemoteSplat` applies every dab in
the message synchronously inside the WebSocket handler (06:2355), and each dab costs `mult`
splat passes — `mult` being the *sender's* arm multiplier, up to 8. Worst case at 8 users is
~150k splat draw calls per second on top of your own sim, with no coalescing to the frame, no
cap, and no drop policy.

The relay is not the bottleneck (p95 fan-out latency 3 ms locally). The client is.

**Fix shape:** push inbound dabs into a queue and drain it in 05j under the same
`__dabDrainBudget`, instead of applying them at message-arrival time. Optionally scale
`DAB_MAX_PER_MSG` / `DAB_FLUSH_MS` by `connectedClients` — the server already reports it.

### 1.2 Any of the 8 can wipe the shared canvas — no confirmation, no undo

`clearCanvas()` (04f:43) wipes and broadcasts. The only gate is Take Turns
(`__mpTurnBlocked`). With turns off, one Clear ends everyone's painting. There is no kick, no
ban, and no undo of a remote clear.

**For test day:** run with Take Turns on, or add a confirm when `connectedClients > 1`.

### 1.3 Remote cursors rebuild every cursor element on every cursor message

`updateRemoteCursors` (06:2539) calls `clearRemoteCursors()` (06:2552), which removes **every**
`.remote-cursor` element — so the `if (!cursorEl)` reuse branch below it can never hit, and all
N elements are recreated. At 8 users that is ~140 cursor messages/s × 7 elements ≈ 1000 DOM
create/destroy cycles per second on a main thread already feeding the GPU. It also defeats the
element's own `transition: left/top` — cursors jump instead of gliding.

Cheap, high-value fix: update existing elements in place; remove only ids no longer in the map.

### 1.4 Chunk-reassembly buffers are sized for a 2-person room

`shapeChunkBuffers.size >= 8` (06:1794) and `colliderChunkBuffers.size >= 8` (06:1999) drop any
*new* transfer once 8 are in flight. On every join all existing members republish their walls at
once (see 1.5), so 7 peers with two walls each already exceeds it. Dropped transfers are silent
and permanent — nothing retries.

### 1.5 Every join triggers a room-wide republish storm, and the receiver rebuilds rather than dedupes

On any `client-count` increase each client clears its publish ledger and resends every wall it
owns (06:1455-1468). The receiver has no rev check: `applyPeerCollider` calls
`removePeerCollider` then `addFromDepth` again, plus `updateObstacleFromLayers()` and
`renderLayers()` (06:2013-2052). Filling a room to 8 fires that on every arrival — measured
count history `2,3,4,5,6,7,8`, so six storms. Expect a visible hitch each time somebody joins.

### 1.6 Peer assets are never released when a peer leaves

`dropPeerAssets()` runs only on **our own** disconnect (06:1367, 06:1662). Nothing handles a
*peer* leaving — `client-count` does not say who left. A departed peer's walls stay in
everyone's simulation and layer list for the rest of the session. `__peerOwner` is set with the
comment "marks it for cleanup when they leave" (06:2047), and nothing consumes it for that.

### 1.7 A reconnecting peer becomes a brand-new person

Verified: the same device reconnecting gets a fresh `clientId` UUID (no `_pk` id on the connect
URL, 06:1305). Every peer-keyed structure is keyed on it, so one reconnect gives you their walls
duplicated (the old ones orphaned by 1.6), a new cursor colour and a new "Artist-XX" name
mid-session, and their brush stamps re-uploaded under new ids — `PEER_MAX` is 48
(33-brush-shapes.js:110), which is reachable across an 8-person session with a few blips.

### 1.8 Peer colliders bypass MAX_LAYERS

`MAX_LAYERS` is 10 (01-config.js:1) and enforced everywhere the user adds a layer (04f:354,
04g:443). `addCollisionLayer` (23:618) has **no** capacity check — it takes `maxIndex + 1` and
creates a div. Peer walls therefore run past the cap into dynamically-created layer divs, and
combined with 1.6 and 1.7 there is no upper bound at all.

## 2. Fairness / security gaps

### 2.1 Take Turns does not gate walls or brushes

Probed with a confirmed non-holder sending each type:

```
splat            blocked          collider-add     RELAYED to watchers
clear            blocked          collider-remove  RELAYED to watchers
preset           blocked          brush-shape      RELAYED to watchers
turn-state       blocked          cursor           RELAYED  (intended)
```

While somebody else has the brush, a watcher can drop an obstacle into their fluid or delete
another person's wall. The fix is one line — add `collider-add`, `collider-remove`,
`brush-shape` to `TURN_HOLDER_ONLY` (party/index.ts:26) — but it needs a relay deploy, so it
rides with §0.

### 2.2 `host-changed` leaks the device uid

Verified: the message carries the raw uid (`host-changed -> turn-uid-1`, party/index.ts:484).
Everything else deliberately maps members to connection ids so the lock's re-admission key never
reaches other clients; this one message hands it over. Anyone who has seen it can present that
uid to re-enter any locked room whose code they know.

### 2.3 The lock only stops people who have never been in the room

`members` is an ever-growing allowlist (party/index.ts:198) and admission checks against it
(party/index.ts:172). Anyone admitted once is re-admittable forever, and there is no kick. So
locking the room *after* a griefer arrives does nothing.

## 3. Smaller things worth knowing

- **8-minute rotations.** Default *1 minute turns* × 8 people means the last person waits 7
  minutes for a first turn. Consider defaulting the session to 30s, or *One swirl each* once §0
  is deployed.
- **Look-mirror cost.** While the settings lock or a turn is live, the host broadcasts up to a
  ~14KB look snapshot every 400ms while dragging (06:517), and each of 7 guests applies a full
  preset snapshot per message.
- **Oversize messages vanish silently.** Verified: a 16.7KB message is dropped with no feedback
  to the sender. Handled for the look snapshot (`fitLookSnapshot`); any new message type
  inherits the trap.
- **Correct, and worth not worrying about:** capacity (9th client refused 4002), host transfer
  on host leave, rotation upkeep on leave, `client-count` accuracy across joins and leaves,
  `turn-pass` round trip, server-authored forgery rejection, heartbeat swallowing.

## 4. Suggested order before the test

1. `npm run deploy` — otherwise everything else is moot (§0).
2. Budget inbound dabs to the frame (§1.1). Single biggest determinant of whether 8 people feel
   good or feel broken.
3. Cursor element reuse (§1.3). Small diff, immediate relief.
4. Guard Clear when more than one person is in the room (§1.2).
5. Raise the two chunk-buffer caps and skip re-apply when the rev is unchanged (§1.4, §1.5).
6. Drop a peer's walls and stamps when they leave, keyed on a stable id rather than the
   connection id (§1.6, §1.7).
7. Ship the `TURN_HOLDER_ONLY` additions with the same deploy (§2.1).
