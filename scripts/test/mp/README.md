# Multiplayer probes

Headless WebSocket clients that speak the same wire protocol as the client (`js/06a…06e-mp-*.js`), for
measuring relay behaviour without opening eight browsers. Written for the 2026-08-23 audit
(`MP-AUDIT-2026-08-23.md` at the repo root).

Start a relay first — everything except `mp-prod-version.js` points at `127.0.0.1:1999`:

```bash
npx partykit dev --port 1999
```

| script | what it answers |
|---|---|
| `mp-load.js` | How much traffic does one client have to absorb when 8 people paint at once? Reports per-client msgs/s, KB/s, fan-out latency, peer dabs/sec, and whether an oversize message is dropped silently. |
| `mp-turns.js` | Does the 8-person rotation hold? Also fires every message type from a **non-holder** to see which ones Take Turns actually gates. |
| `mp-callreturn.js` | Does **Call and return** (stroke mode) hold? No deadline on the wire, the idle backstop passes a quiet holder after `STROKE_IDLE_MS` and a paint message pushes it out, `turn-pass` still works, and the removed settings-share messages are inert. Slow (~2.5 min): it waits out the real backstop. |
| `mp-lobby-ttl.js` | Can a waiter whose keep-alives run LATE still be found? Holds a lobby pin open with no keep-alive for `LATE_MS` (default 75 s), then sends a second seeker and expects it to be paired into the waiter's room; then closes the pin and expects a third seeker to get a fresh room. Proves the margin between the client's 40-50 s keep-alive and the lobby's `WAIT_TTL_MS`. |
| `wire-loopback.js` | **Browser console harness**, not a Node probe: does a peer see the stroke the painter painted? Paints a synthetic stroke while capturing the wire messages on a fake socket, replays them through the real receive path on the same canvas at their original timing, and compares the dye (correlation, dye ratio, roughness) plus how the drain paced the dabs. Paste into the console, then `await __lb.A()`, `await __lb.B()`, `__lb.report()`. Found the ±1 velocity clamp on 2026-09-11. |
| `mp-text.js` | Text and wall messages on the relay (2026-09-15): `text-line` / `text-line-remove` / `text-pour` / `collider-edit` relay stamped with the sender in free painting, are dropped from a watcher and relayed from the holder while turns run (including edits of someone else's wall or line, `own`), and `peer-left` names who left by connection id, never uid, and cannot be forged. `BACKSTOP=1` adds the slow Call-and-return check that typing a line counts as holder activity. `MP_HOST=127.0.0.1:8787` for wrangler dev. |
| `mp-text-e2e.js` | **Two real headless Chromes** (separate profiles = two device uids) running this working tree against a local relay (`npx wrangler dev --port 8787 --ip 127.0.0.1`; it reads `public/`, never builds it). Checks what LANDED on each canvas — the peer's DOM line, the obstacle texture, the dye — for text lines and walls, typing, Fluidize and held-key pours, turn staging, Paint Collider walls, Collision on/off, edited masks, editing each other's walls and lines (edits land on the author's own objects; delete switches off / hides), a reconnect, and leaving. ~40 s, 49 checks. Built-in static server, no dev server needed. |
| `mp-pad.js` | Phone brushes on the relay (2026-09-16): a pad (`?kind=pad`, phone/phone.js) is never made host — alone in an empty room, when the host leaves, or sharing the host's device id — and a canvas joining a pads-only room takes the seat, so a computer that reloads while its phone stays connected gets its room back. Also: `pad-hello` / `pad-info` and a pad's strokes, cursor and pointer-up relay stamped with the sender; pads are in the turn order, gated like anyone out of turn, can paint and pass on their turn, and cannot stop turns. `MP_HOST=127.0.0.1:8787` for wrangler dev. ~8 s, 24 checks. |
| `mp-phone-e2e.js` | **The phone brush as an artist, end to end**: one headless Chrome runs this working tree's app (or the deployed one with `APP_URL=https://swirltogether.com/`), a second emulates an iPhone that opens the room link, is sent to `phone/` and paints with touch — against a local relay (`npx wrangler dev --port 8787`) unless `APP_URL` is set. Checks the "Paint from your phone" door and dialog (opened on As your mouse with no room, then As an artist: room, QR, no clipboard; a click before the room client has loaded — `?delay06=1`), the redirect, `pad-info` (canvas size, flow model, the brush and how it walks), that the phone is only the pad (no brush controls; upright it takes the width, sideways the full height, the corner chrome never on it, even with turns), that it follows a size change made on the computer, dye landing on the computer as much as and where the same stroke painted there lands (fixed and random colours, time-matched), the phone cursor mark, Take turns and Call and return from the phone, Clear, the computer reloading (host again, phone re-counted), leaving, the installed app (Chrome's own installability verdict, the manifest and its icons, the service worker taking control, the offline page — the built-in server can drop its connections — Rejoin, the install card with and without a browser install prompt, and the home-screen landing), and `?full=1`. `SHOTS=<dir>` saves screenshots. ~40 s, 70 checks. |
| `mp-phone-mouse.js` | **The phone as the computer's mouse, end to end** (2026-09-17): four headless Chromes — the app (A), an emulated iPhone (B) that opens A's 8-character mouse link (`sys-mouse-<CODE>`, js/55-phone-mouse.js), a second canvas (C) in a room with A, and a second phone (D) — against a local relay unless `APP_URL` is set. Checks the dialog opening on As your mouse with no room (QR, grouped code, no clipboard), the phone connecting and saying so on both ends, the pad taking the canvas shape, a phone touch playing in as one press / its moves / one lift and laying as much dye as the same mouse stroke in the same place, the computer's colour and brush size deciding the phone's stroke, a still finger keeping the stroke down while a silent phone is let go of, a room seeing the phone's strokes as the computer's own (no phone member, no phone cursor), the door from inside a room (a row of the room panel, surviving the stranger swirl and the wait for one, which both hide the invite block; the artist way explains itself while the lobby looks, rather than starting a room) and a phone pairing there while the computer is already in a room, the computer's turn and Pass on the phone (blocked out of turn, with the reason), Call and return, Clear (for the room too), a second phone taking over and Use this phone taking it back, Disconnect and Reconnect, the computer reloading onto the same code, the artist way and the stranger-swirl note in the same dialog, Disconnect on the computer (new code, the phone told why, idle close), and the phone's start page (two ways, typing either kind of code). `SHOTS=<dir>` saves screenshots. ~45 s, 77 checks. |
| `mp-count.js` | Does the "N artists here" count stay truthful across joins and leaves? |
| `mp-id.js` | Does one device keep one `clientId` across a reconnect? (Everything peer-keyed depends on this.) |
| `mp-prod-version.js` | Which relay build is **live**? Two ordinary connections to a random room code on the deployed host; both close at the end. Run it after every `npm run deploy`. |

Env knobs on `mp-load.js`: `MP_HOST`, `MP_ROOM`, `MP_N`, `MP_PAINTERS`, `MP_SECONDS`.

Painting rates are pinned to the real ones — 96 dabs per message (`DAB_MAX_PER_MSG`) at ~42
flushes/sec, which is the 4000 dab/s `BRUSH_DAB_BUDGET` — so the numbers describe the product,
not the probe. If those constants change in `06d-mp-paint-wire.js` or `04a-canvas-gl-config.js`,
change them here too.
