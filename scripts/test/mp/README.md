# Multiplayer probes

Headless WebSocket clients that speak the same wire protocol as the client (`js/06a…06e-mp-*.js`), for
measuring relay behaviour without opening eight browsers. Written for the 2026-08-23 audit
(`notes/audits/MP-AUDIT-2026-08-23.md`).

Start a relay first — everything except `mp-prod-version.js` points at `127.0.0.1:1999`:

```bash
npx partykit dev --port 1999
```

| script | what it answers |
|---|---|
| `mp-load.js` | How much traffic does one client have to absorb when 8 people paint at once? Reports per-client msgs/s, KB/s, fan-out latency, peer dabs/sec, and whether an oversize message is dropped silently. |
| `mp-lobby-ttl.js` | Can a waiter whose keep-alives run LATE still be found? Holds a lobby pin open with no keep-alive for `LATE_MS` (default 75 s), then sends a second seeker and expects it to be paired into the waiter's room; then closes the pin and expects a third seeker to get a fresh room. Proves the margin between the client's 40-50 s keep-alive and the lobby's `WAIT_TTL_MS`. |
| `wire-loopback.js` | **Browser console harness**, not a Node probe: does a peer see the stroke the painter painted? Paints a synthetic stroke while capturing the wire messages on a fake socket, replays them through the real receive path on the same canvas at their original timing, and compares the dye (correlation, dye ratio, roughness) plus how the drain paced the dabs. Paste into the console, then `await __lb.A()`, `await __lb.B()`, `__lb.report()`. Found the ±1 velocity clamp on 2026-09-11. |
| `mp-text.js` | Text and wall messages on the relay (2026-09-15): `text-line` / `text-line-remove` / `text-pour` / `collider-edit` relay stamped with the sender, from anyone (including edits of someone else's wall or line, `own`) — asking for turns starts none since 2026-10-06 — and `peer-left` names who left by connection id, never uid, and cannot be forged. `MP_HOST=127.0.0.1:8787` for wrangler dev. |
| `mp-text-e2e.js` | **Two real headless Chromes** (separate profiles = two device uids) running this working tree against a local relay (`npx wrangler dev --port 8787 --ip 127.0.0.1`; it reads `public/`, never builds it). Checks what LANDED on each canvas — the peer's DOM line, the obstacle texture, the dye — for text lines and walls, typing, Fluidize and held-key pours, everyone's text and walls going out as they are made, Paint Collider walls, Collision on/off, edited masks, editing each other's walls and lines (edits land on the author's own objects; delete switches off / hides), a reconnect, and leaving. ~40 s, 49 checks. Built-in static server, no dev server needed. |
| `mp-panel-e2e.js` | **Three real headless Chromes** against a local relay (`npx wrangler dev --port 8788 --ip 127.0.0.1`; `MP_HOST` overrides) read the room panel as each person sees it (2026-10-04 redesign; shared settings since 2026-10-06): the one status line ("Sharing settings · N here") and its dot, the activity line (the welcome, then who changed what in their colour), the same three controls for host and guest (Invite, ⋯, Leave), the Invite popover (Code / QR / Hide, copy, the phone door) and the ⋯ menu, Lock room, a stranger pair (📱 Phone, no locks, sharing settings — local relay only, since it goes through the lobby; `STRANGER=1` forces it), and Hide sticking until it is changed (after a reload, in a new room, on every open of Invite and of the phone dialog). Runs the button audit over the panel and both popovers. ~15 s, 47 checks. `SHOTS=<dir>` saves a screenshot per state. |
| `mp-pad.js` | Phone brushes on the relay (2026-09-16): a pad (`?kind=pad`, phone/phone.js) is never made host — alone in an empty room, when the host leaves, or sharing the host's device id — and a canvas joining a pads-only room takes the seat, so a computer that reloads while its phone stays connected gets its room back. Also: `pad-hello` / `pad-info` and a pad's strokes, cursor and pointer-up relay stamped with the sender; asking for turns starts none and a pad paints like anyone (rooms have no turns since 2026-10-06). `MP_HOST=127.0.0.1:8787` for wrangler dev. ~8 s, 24 checks. |
| `mp-phone-e2e.js` | **The phone brush as an artist, end to end**: one headless Chrome runs this working tree's app (or the deployed one with `APP_URL=https://swirltogether.com/`), a second emulates an iPhone that opens the room link, is sent to `phone/` and paints with touch — against a local relay (`npx wrangler dev --port 8787`) unless `APP_URL` is set. Checks the "Paint from your phone" door and dialog (opened on As your mouse with no room, then As an artist: room, QR, no clipboard; a click before the room client has loaded — `?delay06=1`), the redirect, `pad-info` (canvas size, flow model, the brush and how it walks), that the phone is only the pad (no brush controls; upright it takes the width, sideways the full height, the corner chrome never on it), that it follows a size change made on the computer, dye landing on the computer as much as and where the same stroke painted there lands (fixed and random colours, time-matched), the phone cursor mark, no turn state or Pass button on the phone, Clear, the computer reloading (host again, phone re-counted), leaving, the installed app (Chrome's own installability verdict, the manifest and its icons, the service worker taking control, the offline page — the built-in server can drop its connections — Rejoin, the install card with and without a browser install prompt, and the home-screen landing), that the phone page has no way into the full app and Send yourself the link (the share sheet, else the clipboard), `?full=1` (unadvertised, for testing), and who gets the pad (a foldable opened flat, as a phone; an Android tablet, an iPad whose Safari says Macintosh and an Android tablet asking for desktop sites, as a tablet; a Mac keeps the full app). `SHOTS=<dir>` saves screenshots. ~45 s, 78 checks. |
| `mp-phone-mouse.js` | **The phone as the computer's mouse, end to end** (2026-09-17): four headless Chromes — the app (A), an emulated iPhone (B) that opens A's 8-character mouse link (`sys-mouse-<CODE>`, js/55-phone-mouse.js), a second canvas (C) in a room with A, and a second phone (D) — against a local relay unless `APP_URL` is set. Checks the dialog opening on As your mouse with no room (QR, grouped code, no clipboard), the phone connecting and saying so on both ends, the pad taking the canvas shape, a phone touch playing in as one press / its moves / one lift and laying as much dye as the same mouse stroke in the same place, the computer's colour and brush size deciding the phone's stroke, a still finger keeping the stroke down while a silent phone is let go of, a room seeing the phone's strokes as the computer's own (no phone member, no phone cursor), the door from inside a room (a row of the room panel, surviving the stranger swirl and the wait for one, which both hide the invite block; the artist way explains itself while the lobby looks, rather than starting a room) and a phone pairing there while the computer is already in a room, no turn and no Pass on the phone (the computer's `mouse-info` carries no `turn`), Clear (for the room too), a second phone taking over and Use this phone taking it back, Disconnect and Reconnect, the computer reloading onto the same code, the artist way and the stranger-swirl note in the same dialog, Disconnect on the computer (new code, the phone told why, idle close), and the phone's start page (two ways, typing either kind of code). `SHOTS=<dir>` saves screenshots. ~45 s, 77 checks. |
| `mp-count.js` | Does the "N artists here" count stay truthful across joins and leaves? |
| `mp-id.js` | Does one device keep one `clientId` across a reconnect? (Everything peer-keyed depends on this.) |
| `mp-prod-version.js` | Which relay build is **live**? Two ordinary connections to a random room code on swirltogether.com (`MP_HOST` overrides); both close at the end. Says whether `room-look` relays, whether turns and the look lock are retired there (2026-10-06), and whether the rotation code itself is gone (a host's `turns` off no longer gets a `turn-state`). Run it after every `npm run deploy:cf`. |
| `mp-share-e2e.js` | **A room shares one set of settings** (2026-10-06): two headless Chromes in a room. The host welcomes a newcomer onto the room's settings (sliders, switches, menus, gravity) while their brush stays theirs; a slider moved on one screen GLIDES on the other (values strictly between, never past, ~420 ms to 95%) and lights up in the mover's colour with "X changed Y"; a stepped control jumps; both directions and two sliders at once; brush and colour mode stay personal; five idle seconds with the kaleidoscope spinning send nothing; a hand on a gliding slider wins; an older build's look is converted (Vibrance units); a 14-slider burst costs ~0.3 ms a glide frame. Works against the live relay (`MP_HOST=swirltogether.com`). ~30 s, 36 checks. |
| `mp-look-parity-e2e.js` | Does everyone in a room end up running EXACTLY the same settings? BOTH sides pushed to different values for every registry control, then the whole `config`, every control and the look globals diffed (personal keys left out, and checked to have stayed put): the welcome, edits from either side, both at once, a quiet room with everything animating, gravity both ways, per-person switches. `MP_HOST=swirltogether.com` works. ~40 s, 14 checks. |
| `relay-retired-turns.js` | The relay with turns and the look lock retired (2026-10-06), run **in-process** (party/index.ts compiled with esbuild, a mock room — no server): an old client's `turns` on/off and `turn-pass` are swallowed (not even the host gets a rotation; nothing relayed, no `turn-state`), a stranger's invite gets a plain no, settings-lock and turn-look never relay, the relay stores no rotation and a room stored with one wakes without it, and `room-look` relays stamped with the sender. Also what stayed: a dirty restart rebuilds the room around the first one back, and heartbeats arm the sweep alarm that reaps a silent pinger. `RELAY_DIR=<dir>` runs it against another copy of party/ (HEAD before 2026-10-06 fails 10; the first retirement, rotation still in the file, fails 2). ~1 s, 17 checks. |

Env knobs on `mp-load.js`: `MP_HOST`, `MP_ROOM`, `MP_N`, `MP_PAINTERS`, `MP_SECONDS`.

Painting rates are pinned to the real ones — 96 dabs per message (`DAB_MAX_PER_MSG`) at ~42
flushes/sec, which is the 4000 dab/s `BRUSH_DAB_BUDGET` — so the numbers describe the product,
not the probe. If those constants change in `06d-mp-paint-wire.js` or `04a-canvas-gl-config.js`,
change them here too.
